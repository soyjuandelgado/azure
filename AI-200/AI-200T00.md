App Service se baja el contenedor del origen y lo ejecuta.

La opción preferida es ACR (Azure Container Registry) porque todo queda en privado y no se depende de otros servicios.

![[Pasted image 20261117094445.png]]

Los puertos 80, 8080 se exponen a internet como 443.

Los certificados se quedan en el App Service para que no sea necesario necesario tenerlos en cada contenedor.

Hay un servicio en azure que guarda todos los secretos: Azure Key Vault.

El contenedor pude conectarse al Key Vault para conseguir los datos a través del App Service. Lo hace cuando se crea.

## Implementación y administración de aplicaciones en Azure Container Apps

1. **App Service**: un solo contenedor
2. **Container Instances**: varios contenedores con una sola entrada/salida a internet
3. **Container Apps**: similar a Kubernetes pero sin trabajar con infraestructura. Permite el pago por uso también
4. **AKS (Kubernetes)**: el más profesional. Hay que configurarla la parte de infra.

### Container Apps

#### Implementación de contenedores

![[Pasted image 20261117113024.png]]

![[Pasted image 20261117113057.png]]

Tienen acceso al mismo entorno de red dentro del mismo environment. Hay un DNS privado para localizar los contenedores.

Alfa, beta, release candidate, produccion: se van moviendo los contenedores de un entorno al otro.

El archivo YAML define el ciclo de vida de tu contenedor. Se trabaja como infrastructura como código. Hay que trabajarlo por consola.

#### Administración de contenedores

![[Pasted image 20261117115136.png]]

Las pruebas de vida son accesos a un nodo via api, que tiene que hacer algo más que simplemente la conexion para asegurar que ese nodo funciona. Tiene que hacer una ejecución simple para confirmarlo, por ejemplo, buscar un dato básico a BD

![[Pasted image 20261117115534.png]]

Nueva imagen con un nuevo numero de versión. 

Después de hacer todas las pruebas se puede realizar el swap a producción.

CNM caché: frontDoor -> contenedor App. FrontDoor cachea la respuesta estática para no necesitar ir constantemente al contenedor.

![[Pasted image 20261117120708.png]]

En el caso de que no se pasen las pruebas.

Errores transitorios: por ejemplo un contenedor depende de otro de BD. Se hacen varios reintentos, ahora, en 30seg y en 5 min.

Si no es un error de transitorio, no pasa a producción.

![[Pasted image 20261117121519.png]]

![[Pasted image 20261117121558.png]]

Hay que tener en cuenta la carga del contenedor y los bloqueos de contenido. Hay que esperar a que cargue todo.

Un modelo de IA puede tardar bastante en contestar. Hay que tenerlo en cuenta para ser generoso con los timeouts.

En error 500 de un proveedor no debe generar un 500 en tu contenedor.

![[Pasted image 20261117122042.png]]


Si se encuentran fallo de "out of memory" hay que ampliar memoria por contenedor. 

Si hay problemas de CPU, la app irá lenta.

#### Como escalar los contenedores

![[Pasted image 20261117123234.png]]

El sistema de escalado responde más rápido que otras opciones.

Puede crecer tanto como puedas pagar.

![[Pasted image 20261117124707.png]]

Prometheus: guarda las métricas de todos tus servicios.

Se pueden usar todo este tipo de eventos para escalar.

Si te pasas de memoria, reinicia el programa; si te pasas de CPU, va más lento.
